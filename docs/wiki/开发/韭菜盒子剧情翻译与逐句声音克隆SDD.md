# 韭菜盒子剧情翻译与发言轮次声音克隆 SDD

> 日期：2026-07-30  
> 状态：克隆校对工作台与人物建议已实施并通过验证
> 范围：仅修改 `peiyin-pyvideotrans`；`jiucaihezi-app` 只作只读参考

## 1. 一句话目标

将一集约两分钟的中文短剧识别并翻译为自然的美式英语对白，由用户在翻译校对窗口确认相邻字幕是否属于同一次连续发言，再以完整发言轮次的中文原声克隆英文语音，最后按逐句字幕时间轴合成完整英文音频或视频。

## 2. 成功标准

1. 用户只需配置 API URL 和 API Key；默认 URL 为 `https://api.jiucaihezi.studio/v1`，并可从设置页前往 `https://api.jiucaihezi.studio/keys`。
2. 翻译固定使用 `gemini-3.6-flash`，一次提交整集 SRT，使人物关系、指代、语气和前后剧情可共同参与翻译。
3. 输出字幕与输入字幕保持严格一一对应，行号和时间戳不变；英文适合美国短剧口语和 TTS 配音，不做逐字直译。
4. 字幕始终逐句保留；连续发言可由用户合并为一次克隆，`A → B → A` 必须形成三个独立轮次。
5. 继续使用现有音频调速、补静音、时间轴对齐和最终合成流程。
6. API Key 不写入日志、Wiki、测试样例或任务输出。
7. 克隆模式的校对窗口以字幕和发言轮次为主工作区，不显示无效的预设音色分配功能。

## 3. 已有能力

当前项目已具备主链路，不重写：

- `BaseTrans` 在开启“发送 SRT”和 `aitrans_context` 后，会把整集字幕作为一个 SRT 批次交给 AI 翻译渠道。
- `_stage_dubbing.py` 为每条英文字幕保留对应中文原文 `ref_text`、时间戳和输出文件名。
- `_create_ref_from_vocal()` 按每条字幕时间戳裁出 `ref_wav`。
- `_rate.py` 负责配音片段调速、补静音、时间轴对齐和完整音频拼接。

韭菜盒子只读参考实现已证明云端媒体链路包含：Bearer Key 鉴权、参考音频上传、`/v1/audio/speech` 提交、异步任务轮询和音频结果下载。实施时只复制完成当前任务所需的最小请求合同，不复制 Vue、Pinia、Tauri、媒体任务 Store 或画布编排。

## 4. 翻译设计

### 4.1 模型和调用

- 渠道：新增“韭菜盒子剧情翻译”。
- Base URL：用户可配置，默认 `https://api.jiucaihezi.studio/v1`。
- 模型：固定 `gemini-3.6-flash`，界面不提供模型输入框。
- 协议：复用现有 OpenAI-compatible `POST /chat/completions` 调用和翻译缓存。
- 模式：该渠道强制使用完整 SRT 上下文，不依赖用户另外开启高级选项。

### 4.2 剧情翻译提示词合同

提示词必须要求模型：

1. 先理解整集事件、人物关系、称谓、指代、隐含意图和情绪变化，再翻译每条字幕。
2. 输出当代美国影视对白，而非书面英语或中文句式的英文替换。
3. 保留角色身份、权力关系、攻击性、暧昧、讽刺、威胁和笑点，不擅自弱化或增写剧情。
4. 使用自然缩写和口语表达；根据字幕时长压缩台词，使其适合配音。
5. 严格保持 SRT 块数量、行号、顺序和时间戳，不合并、不拆分、不移动语义到相邻字幕。
6. 人名、地名和专有词在整集中保持一致，并继续遵守现有术语表。
7. 只输出 `<TRANSLATE_TEXT>` 包裹的合法 SRT，不输出分析、剧情总结或解释。

提示词作为产品运行时资源放在 `videotrans/prompts/srt/`。不创建 Codex Skill：Codex Skill 不会自动进入桌面应用的模型请求，单独创建只会形成无法执行的旁路文档。若未来产品增加可选择、可加载的翻译 Skill 机制，再将这份提示词合同迁移为产品 Skill。

### 4.3 人物与发言轮次建议

不把 `Speaker1:` 写入 SRT 字幕正文。现有翻译响应必须继续保持纯 SRT，避免人物前缀进入最终字幕和 TTS 文本。

剧情翻译成功后，仅在“韭菜盒子剧情翻译 + Qwen3-TTS 本地 + clone”组合下，使用同一组 API URL、Key 和固定模型 `gemini-3.6-flash` 发起一次独立轻量请求。输入包含整集中文、整集英文、时间轴以及 `speaker.json` 的音频说话人提示；输出只包含与字幕逐行对应的 JSON：

```json
[
  {"line": 1, "speaker": "Speaker1", "join_previous": false},
  {"line": 2, "speaker": "Speaker2", "join_previous": false},
  {"line": 3, "speaker": "Speaker2", "join_previous": true}
]
```

建议写入任务缓存目录的 `turn_suggestions.json`，不直接作为配音合同。必须校验行数、行号、人物标签和布尔类型；请求或校验失败时记录不含 Key 的警告并回退 `speaker.json`，不得中断已经成功的翻译。

校对窗口预填优先级固定为：已有合法 `turns.json` > `turn_suggestions.json` > 现有音频说话人及 1000ms 间隔规则。人物标签仅帮助人工识别 `A → B → A`，最终 Qwen3-TTS 仍只消费人工保存的 `turns.json`。

## 5. 发言轮次声音克隆设计

“韭菜盒子云端克隆”和本地 Qwen3-TTS 继续消费现有克隆字段：

```text
英文输出文本  = data_item.text
中文参考文本  = data_item.ref_text
参考声音文件  = data_item.ref_wav
生成文件      = data_item.filename
目标语言      = English
```

最小请求流程：

```text
ref_wav
  -> 编码为 data:audio/wav;base64 节点值
  -> POST /v1/audio/speech（声音克隆应用合同；服务端适配器负责上传）
  -> 同步获得音频 URL，或按返回 taskId 轮询
  -> 下载并转换为 data_item.filename
  -> 交回现有对齐与合成流程
```

### 5.1 人工分组合同

翻译完成、配音开始前，复用现有字幕校对窗口增加“接上句”列：

- 未勾选：从本句开始新的克隆任务；
- 勾选：本句与上一句合为同一次克隆；
- 第一行固定不可勾选；
- `speaker.json` 只负责自动预填，人工勾选结果是最终依据；
- 只允许时间轴相邻字幕合并，不跨行寻找相同人物；
- 字幕文本仍可逐句编辑、保存和最终显示。

保存按钮显示“保存翻译与分组，开始配音”，并将分组写到目标字幕同目录：

```json
[false, true, false, true]
```

文件名固定为 `turns.json`，数组与字幕行严格一一对应。优先读取已有合法文件；不存在时，仅在相邻说话人相同且原声间隔为 `0..1000ms` 时预勾选。缺少说话人数据时全部不勾选。

### 5.2 配音执行

配音阶段仅在 Qwen3-TTS 本地克隆中消费 `turns.json`。文件存在且数组长度、类型合法时完全服从人工结果；文件缺失或损坏时保留现有 `speaker.json` 自动合并作为兼容回退。合并后的单次 TTS 任务使用整段英文、整段中文参考文本和从首句开始到末句结束的原声音频，生成后仍由现有 `_subtitle_items` 展开回逐句字幕时间轴。

不建立长期 voice ID，不新增人物管理页。短句、重叠对白或背景音乐仍会限制克隆质量，但不能静默改用其他人的参考音频。

### 5.3 克隆校对工作台

仅当配音渠道为 Qwen3-TTS 本地且主角色为 `clone` 时，现有通用角色分配窗口切换为克隆校对模式：

- 单视频交互明确显示步骤：第 1 步“校对中文字幕并开始翻译” → 第 2 步“校对英文与发言轮次” → 可选步骤“复核配音后的英文字幕”；
- 第 2 步必须使用任务启动时冻结的 `voice_role` 判断 clone 模式，不读取可能已变化的主界面下拉框；

- 顶部只保留“字幕句数 / 克隆段数”和英文字幕查找替换，不自动倒计时继续；
- 主区域使用横向分割，左侧为约 280px 宽的 9:16 视频预览和播放状态，右侧表格占剩余空间；
- 表格隐藏 `Sel` 和“配音角色”，保留“行、人物建议、接上句、播放、英文字幕、中文原文”，时间轴压缩显示；
- 人物建议优先显示模型建议，缺失时显示音频说话人标签，但不参与最终音色选择；
- 隐藏说话人角色分配、给选中字幕指定角色、配音角色下拉框和旧试听功能；
- 隐藏“不保存只继续”，保留“打开输出目录”“终止任务”和唯一主按钮“确认字幕与分组，开始配音”；
- 打开窗口时不自动播放，用户点击行内播放按钮试听对应原声。

非 clone 或其他 TTS 渠道继续使用原有通用角色分配界面，不改变现有能力。

## 6. 设置界面

为翻译和克隆共用一组“韭菜盒子 API”配置：

- API URL 输入框，预填 `https://api.jiucaihezi.studio/v1`；
- API Key 密码输入框，支持显示和隐藏；
- “前往获取”打开固定地址 `https://api.jiucaihezi.studio/keys`；
- “测试连接”使用 Bearer Key 请求 `/v1/models`；
- “保存”。

参考音频直接以内嵌 `data:audio/wav;base64` 节点值提交；线上 API 未公开 `/api/creations/uploads`，由服务端 RunningHub 适配器负责媒体上传。翻译和声音任务使用 `/v1` Base URL。

## 7. 失败与安全

- 缺少 URL、Key 或参考音频时，在付费请求前失败并指出缺失项。
- `401/403` 显示 Key 无效或无权限；`429` 显示请求频繁；任务失败显示服务端消息但不得拼入 Key。
- 单条克隆失败时停止任务并保留缓存，不以静音伪装成功，用户修复后可利用已有翻译和已完成片段重试。
- 默认单线程提交云端克隆，避免付费任务并发、限流和乱序；确认服务额度和稳定性后再考虑提高并发。
- 下载结果只接受服务端返回的 HTTP(S) 音频地址或合法音频内容。
- `turns.json` 非布尔数组或与字幕行数不一致时记录警告并回退自动分组，不中断已有任务。

## 8. 最小改动范围

预计只涉及：

1. 新增一个 OpenAI-compatible 剧情翻译薄通道及一份 SRT 提示词。
2. 新增一个韭菜盒子云端克隆 TTS 实现，并在现有 TTS 注册表末尾追加 ID。
3. 增加共用 URL、Key、获取 Key 和测试连接设置。
4. 增加一次独立的人物与发言轮次建议请求及严格 JSON 校验，失败时回退现有音频建议。
5. 在现有字幕校对表增加一列复选框、分组摘要和保存逻辑，并为 clone 模式条件化精简布局。
6. 增加最小合同测试：整集 SRT 单次翻译、人物建议解析与回退、参考音频上传、人工分组优先、同步/异步结果解析、Key 不进入日志。

不修改现有识别、说话人识别、音频对齐和视频合成算法；不修改 `jiucaihezi-app`。

## 9. 实施顺序与验证

```text
1. 翻译薄通道 -> 验证：一份多人物测试 SRT 只发出一次请求，输出块数和时间戳完全一致
2. 云端克隆通道 -> 验证：一条 3-10 秒中文参考音频成功生成英文 WAV
3. 接入现有流水线 -> 验证：多条字幕各自使用对应 ref_wav，合成音频总时间轴正确
4. 两分钟真实样片 -> 验证：人工检查人物关系、美国口语、音色、语速和音画同步
5. 人工轮次校对 -> 验证：错误识别为同一人的 A → B → A 可手动拆成三次克隆，字幕仍为三行
6. 克隆校对工作台 -> 验证：竖屏预览位于左侧、表格占主区域、角色控件隐藏且其他 TTS 界面不受影响
```

真实 Key、声音克隆应用当前 `webappId`、节点字段和实际扣费任务返回结构只能通过一次小额端到端调用最终确认；确认前不能把方案状态标记为已完成。
