# 韭菜盒子剧情翻译与逐句声音克隆 SDD

> 日期：2026-07-30  
> 状态：代码与模拟合同已完成，待真实付费验证  
> 范围：仅修改 `peiyin-pyvideotrans`；`jiucaihezi-app` 只作只读参考

## 1. 一句话目标

将一集约两分钟的中文短剧音频识别为带时间戳的字幕，使用 `gemini-3.6-flash` 结合整集剧情上下文翻译为自然的美式英语对白，再以每句中文原声为参考音频逐句克隆英文语音，最后按原时间轴合成完整英文音频或视频。

## 2. 成功标准

1. 用户只需配置 API URL 和 API Key；默认 URL 为 `https://api.jiucaihezi.studio/v1`，并可从设置页前往 `https://api.jiucaihezi.studio/keys`。
2. 翻译固定使用 `gemini-3.6-flash`，一次提交整集 SRT，使人物关系、指代、语气和前后剧情可共同参与翻译。
3. 输出字幕与输入字幕保持严格一一对应，行号和时间戳不变；英文适合美国短剧口语和 TTS 配音，不做逐字直译。
4. 每条英文字幕使用同时间段的中文原声音频作为克隆参考，生成结果写入现有逐句配音文件。
5. 继续使用现有音频调速、补静音、时间轴对齐和最终合成流程。
6. API Key 不写入日志、Wiki、测试样例或任务输出。

## 3. 已有能力

当前项目已具备主链路，不重写：

- `BaseTrans` 在开启“发送 SRT”和 `aitrans_context` 后，会把整集字幕作为一个 SRT 批次交给 AI 翻译渠道。
- `_stage_dubbing.py` 为每条英文字幕保留对应中文原文 `ref_text`、时间戳和输出文件名。
- `_create_ref_from_vocal()` 按每条字幕时间戳裁出 `ref_wav`。
- `_rate.py` 负责配音片段调速、补静音、时间轴对齐和完整音频拼接。

韭菜盒子只读参考实现已证明云端媒体链路包含：Bearer Key 鉴权、参考音频上传、`/v1/audio/speech` 提交、异步任务轮询和音频结果下载。实施时只复制完成当前任务所需的最小请求合同，不复制 Vue、Pinia、Tauri、媒体任务 Store 或画布编排。

## 4. 翻译设计

### 4.1 模型和调用

- 渠道：新增“韭菜盒子剧情翻译”。
- Base URL：用户可配置，默认 `https://api.jiucaihezi.studio/v1`。
- 模型：固定 `gemini-3.6-flash`，界面不提供模型输入框。
- 协议：复用现有 OpenAI-compatible `POST /chat/completions` 调用和翻译缓存。
- 模式：该渠道强制使用完整 SRT 上下文，不依赖用户另外开启高级选项。

### 4.2 剧情翻译提示词合同

提示词必须要求模型：

1. 先理解整集事件、人物关系、称谓、指代、隐含意图和情绪变化，再翻译每条字幕。
2. 输出当代美国影视对白，而非书面英语或中文句式的英文替换。
3. 保留角色身份、权力关系、攻击性、暧昧、讽刺、威胁和笑点，不擅自弱化或增写剧情。
4. 使用自然缩写和口语表达；根据字幕时长压缩台词，使其适合配音。
5. 严格保持 SRT 块数量、行号、顺序和时间戳，不合并、不拆分、不移动语义到相邻字幕。
6. 人名、地名和专有词在整集中保持一致，并继续遵守现有术语表。
7. 只输出 `<TRANSLATE_TEXT>` 包裹的合法 SRT，不输出分析、剧情总结或解释。

提示词作为产品运行时资源放在 `videotrans/prompts/srt/`。不创建 Codex Skill：Codex Skill 不会自动进入桌面应用的模型请求，单独创建只会形成无法执行的旁路文档。若未来产品增加可选择、可加载的翻译 Skill 机制，再将这份提示词合同迁移为产品 Skill。

## 5. 逐句声音克隆设计

新增一个“韭菜盒子云端克隆”TTS 通道，并加入现有 `SUPPORT_CLONE`。每条任务直接消费现有字段：

```text
英文输出文本  = data_item.text
中文参考文本  = data_item.ref_text
参考声音文件  = data_item.ref_wav
生成文件      = data_item.filename
目标语言      = English
```

最小请求流程：

```text
ref_wav
  -> 编码为 data:audio/wav;base64 节点值
  -> POST /v1/audio/speech（声音克隆应用合同；服务端适配器负责上传）
  -> 同步获得音频 URL，或按返回 taskId 轮询
  -> 下载并转换为 data_item.filename
  -> 交回现有对齐与合成流程
```

第一版按用户要求逐句克隆，不做说话人聚类，也不建立长期 voice ID。短句、重叠对白或背景音乐会限制克隆质量，但不能静默改用其他人的参考音频。

## 6. 设置界面

为翻译和克隆共用一组“韭菜盒子 API”配置：

- API URL 输入框，预填 `https://api.jiucaihezi.studio/v1`；
- API Key 密码输入框，支持显示和隐藏；
- “前往获取”打开固定地址 `https://api.jiucaihezi.studio/keys`；
- “测试连接”使用 Bearer Key 请求 `/v1/models`；
- “保存”。

参考音频直接以内嵌 `data:audio/wav;base64` 节点值提交；线上 API 未公开 `/api/creations/uploads`，由服务端 RunningHub 适配器负责媒体上传。翻译和声音任务使用 `/v1` Base URL。

## 7. 失败与安全

- 缺少 URL、Key 或参考音频时，在付费请求前失败并指出缺失项。
- `401/403` 显示 Key 无效或无权限；`429` 显示请求频繁；任务失败显示服务端消息但不得拼入 Key。
- 单条克隆失败时停止任务并保留缓存，不以静音伪装成功，用户修复后可利用已有翻译和已完成片段重试。
- 默认单线程提交云端克隆，避免付费任务并发、限流和乱序；确认服务额度和稳定性后再考虑提高并发。
- 下载结果只接受服务端返回的 HTTP(S) 音频地址或合法音频内容。

## 8. 最小改动范围

预计只涉及：

1. 新增一个 OpenAI-compatible 剧情翻译薄通道及一份 SRT 提示词。
2. 新增一个韭菜盒子云端克隆 TTS 实现，并在现有 TTS 注册表末尾追加 ID。
3. 增加共用 URL、Key、获取 Key 和测试连接设置。
4. 增加最小合同测试：整集 SRT 单次翻译、参考音频上传、同步/异步结果解析、Key 不进入日志。

不修改现有识别、说话人识别、逐句裁切、音频对齐和视频合成算法；不修改 `jiucaihezi-app`。

## 9. 实施顺序与验证

```text
1. 翻译薄通道 -> 验证：一份多人物测试 SRT 只发出一次请求，输出块数和时间戳完全一致
2. 云端克隆通道 -> 验证：一条 3-10 秒中文参考音频成功生成英文 WAV
3. 接入现有流水线 -> 验证：多条字幕各自使用对应 ref_wav，合成音频总时间轴正确
4. 两分钟真实样片 -> 验证：人工检查人物关系、美国口语、音色、语速和音画同步
```

真实 Key、声音克隆应用当前 `webappId`、节点字段和实际扣费任务返回结构只能通过一次小额端到端调用最终确认；确认前不能把方案状态标记为已完成。
